# ผู้ติดตามสถานการณ์และรายงานประชาชน

หน้า `/` แสดงหน้าประชาชนสำหรับผู้ยังไม่เข้าสู่ระบบและบัญชี `viewer` ส่วนบัญชีเจ้าหน้าที่ใช้ dashboard เดิม เมนูหน้าประชาชนใช้ `#home`, `#map`, `#report`, `#mine` เพื่อเปิดหน้าที่ต้องการโดยตรงและรีเฟรชได้

## การเปิดใช้งาน

1. ใช้ PostgreSQL เดิมและรัน `npm run db:migrate:auth` หากยังไม่มีตารางบัญชี
2. รัน `npm run db:migrate:reports` และ `npm run db:migrate:alerts`
3. ตั้งค่า LINE Login และ callback ตาม README ตั้ง `AUTH_BYPASS=false` สำหรับการใช้งานจริง
4. กำหนด `LINE_ADMIN_USER_IDS` ให้บัญชีผู้ดูแลที่ต้องการ บัญชีใหม่ทุกบัญชีอื่นเริ่มเป็น `viewer` รวมถึงผู้สมัครคนแรก ผู้ดูแลเดิมยังคงสิทธิ์เดิม
5. ผู้ดูแลให้สิทธิ์ `reports:manage` กับเจ้าหน้าที่ผ่านหน้าจัดการสิทธิ์ผู้ใช้

ในโหมดพัฒนา การเข้า `localhost`, `127.0.0.1` หรือ `::1` ให้บัญชีผู้ติดตามทดสอบโดยไม่ต้อง Login LINE บัญชีนี้ส่งรายงานและดูรายงานของตัวเองได้ ระบบสร้างบัญชีในฐานข้อมูลเมื่อส่งรายงานสำเร็จครั้งแรก โดเมนจริง โหมด production และคำขอที่มี forwarded host เป็นโดเมนอื่นยังต้องเข้าสู่ระบบตามปกติ ไม่ให้สิทธิ์ผู้ดูแลจากการเข้า localhost บัญชีจำลองจาก `AUTH_BYPASS` เปิดหน้าจัดการได้ แต่ไม่สามารถส่งหรือเปลี่ยนสถานะรายงานจริง เพราะไม่มี UUID ใน `app_users`

## ฐานข้อมูล

| ตาราง | หน้าที่ |
| --- | --- |
| `app_users` | บัญชี LINE บทบาท และรายการสิทธิ์เดิม |
| `citizen_reports` | ผู้แจ้ง ประเภทเหตุ สถานที่ พิกัด (ไม่บังคับ) เวลาพบเหตุ สภาพถนน รายละเอียด ข้อมูลติดต่อ จำนวนคน ความต้องการ สถานะ และ key ป้องกันส่งซ้ำ |
| `citizen_report_events` | ประวัติสถานะ ผู้ดำเนินการ ข้อความถึงผู้แจ้ง และเวลา |
| `citizen_report_photos` | รูปประกอบสูงสุด 8 รูปต่อรายงาน เก็บ bytea พร้อมชนิดไฟล์ ชื่อไฟล์ และลำดับ รูปละไม่เกิน 5 MB รวมไม่เกิน 20 MB |

ความสัมพันธ์: บัญชีหนึ่งมีหลายรายงาน รายงานหนึ่งมีหลายเหตุการณ์สถานะและมีรูปได้หลายรูป (สูงสุด 8 รูป) FK ของผู้แจ้งป้องกันการลบบัญชีที่ยังมีรายงาน ส่วนผู้ดำเนินการในประวัติใช้ `ON DELETE SET NULL` เพื่อรักษาประวัติ ดัชนีรองรับการอ่านตามผู้แจ้งและคิวสถานะ

การเขียนรายงาน/รูป/ประวัติอยู่ใน transaction เดียวกัน `(reporter_id, submission_key)` ไม่ซ้ำ จึงลองส่งใหม่หลังเครือข่ายหลุดได้โดยไม่สร้างรายงานซ้ำ ใช้ advisory lock ต่อบัญชี จำกัดรายงานใหม่ 5 ฉบับใน 10 นาที

## สิทธิ์และ API

| ผู้ใช้ | ดูสถานการณ์ / ประกาศอนุมัติ | ส่งรายงาน | ดูรายงาน | เปลี่ยนสถานะ |
| --- | --- | --- | --- | --- |
| ไม่เข้าสู่ระบบ | ได้ | เข้าสู่ระบบ LINE ก่อน | ไม่ได้ | ไม่ได้ |
| viewer | ได้ | ได้ | ของตัวเอง | ไม่ได้ |
| operator | ตามสิทธิ์เดิม | เมื่อมี reports:create | ของตัวเอง หรือทั้งหมดเมื่อมี reports:manage | เมื่อมี reports:manage |
| admin | ได้ | ได้ | ทั้งหมด | ได้ |

- `GET /api/reports`: รายงาน 100 รายการล่าสุด กรองเจ้าของบน server ไม่เปิดรายงานส่วนบุคคลต่อสาธารณะ
- `POST /api/reports`: multipart form พร้อม `waterDepth` (unknown/dry/ankle/knee/waist/neck/overhead) และ repeated optional `photos` (ยังรองรับ `photo` เดิม) ตรวจ input, เวลาพบเหตุ, เบอร์โทรศัพท์, พิกัด, จำนวนคน, ประเภทรูปจาก signature และขนาด
- `PATCH /api/reports`: เจ้าหน้าที่เปลี่ยนสถานะและบันทึกข้อความ ส่ง `{ id, status, note }` ตรวจสถานะใน transaction พร้อม row lock
- `GET /api/reports/:id/photo?photoId=:photoId`: ตรวจสิทธิ์เจ้าของ/เจ้าหน้าที่และตรวจว่ารูปอยู่ในรายงานที่ระบุ ก่อนคืนรูป ใช้ private no-store ถ้าไม่ส่ง photoId จะแสดงรูปแรกเพื่อรองรับลิงก์เดิม
- `GET /api/flood-alerts?public=1`: เปิดเฉพาะประกาศอนุมัติที่ยังไม่หมดอายุ แม้ผู้เรียกเป็น admin

ลำดับสถานะ: pending → verified / rejected; verified → in_progress / resolved / rejected; in_progress → resolved. สถานะ resolved / rejected ปิดแล้วและเปลี่ยนซ้ำไม่ได้ ประวัติแสดงถึงผู้แจ้งด้วย จึงต้องเขียนข้อความที่เหมาะกับผู้แจ้ง

## ประสบการณ์มือถือ

เมนูด้านล่าง ปุ่มอย่างน้อย 44–48 px ต้องเข้าสู่ระบบ LINE ก่อนเห็นฟอร์ม และกลับมาที่ #report หลังเข้าสู่ระบบสำเร็จ ฟอร์ม 2 ขั้นตอน รองรับ GPS หรือแตะแผนที่/ลากหมุด พร้อมขอบเขตลุ่มน้ำป่าพะยอมจากเว็บอ้างอิง (public/boundaries/pa-phayom-basin.geojson) หรือพิมพ์สถานที่แทน แนบรูป JPG/PNG/WebP คำขอช่วยเหลือเพิ่มจำนวนคนและสิ่งที่ต้องการ ไม่มีการแสดงว่าสำเร็จเมื่อ DB ยังไม่พร้อม หลังส่งสำเร็จมีเลขรายงานและสถานะรอตรวจสอบ

ตัวเลือกประเภทเหตุ สภาพการเดินทาง ความต้องการช่วยเหลือ และระดับน้ำแสดงเป็นปุ่มพร้อมไอคอน ระดับน้ำ ตาตุ่ม/เข่า/เอว/คอ/มิดหัว เป็นการสังเกตเทียบร่างกาย ไม่ใช่ค่าจากเซ็นเซอร์หรือเกณฑ์เตือนภัย ไม่แปลงเป็นเมตร ร่างจากหน้ารุ่นก่อนยังคืนข้อมูลให้บัญชีที่เข้าสู่ระบบได้ใน 30 นาที ยังไม่มี offline queue และการส่งแบบฟอร์มไม่ใช่การยืนยันรับภารกิจหรือแจ้งเตือนหน่วยกู้ภัยโดยอัตโนมัติ

หน้าแรกใช้ข้อมูลตรวจวัดจาก `/api/situation` ไม่ใช้ค่า telemetry ตัวอย่าง ศูนย์อพยพแสดงเฉพาะข้อมูล database ที่สถานะ open และเวลา updatedAt ไม่เกิน 6 ชั่วโมง จำนวนความจุเป็นทะเบียน ไม่ใช่จำนวนที่ว่าง หน้าแผนที่ยังไม่ได้เสนอเส้นทางนำทางและต้องยืนยันเส้นทางกับเจ้าหน้าที่

## การนำขึ้นระบบ

Migration นี้ยังต้องรันกับฐานข้อมูลปลายทางก่อนใช้รับรายงานจริง สำรองตามกระบวนการของระบบ และทดสอบบัญชี viewer สองบัญชี (ต้องไม่เห็นรายงาน/รูปของกันและกัน) กับ operator ที่มี/ไม่มี reports:manage รวมถึง LINE callback จริง ภาพใน DB เหมาะกับงานเริ่มต้น เมื่อปริมาณเพิ่มควรย้ายไป private object storage พร้อม signed download ตามสิทธิ์เดิม

## การตรวจสอบโค้ด

รัน `npm run lint`, `npm run build` และ `npm run test:reports` การทดสอบที่เก็บในโปรเจกต์ครอบคลุม validation, การตรวจสิทธิ์, การกรองเจ้าของ, transaction, การส่งซ้ำ, rate limit และสถานะที่ปิดแล้ว โดยใช้ mock database

ตรวจเพิ่มเติมระหว่างพัฒนาแล้วด้วย Playwright ที่ 320/390/1440 px (ไม่มี overflow, ฟอร์มบังคับข้อมูล, คืนร่างหลังกลับจาก LINE และเปิดแผนที่ได้) และรัน migration/API กับ PostgreSQL ผ่าน PGlite แบบ in-memory ในฐานข้อมูลแยก เพื่อยืนยัน schema, การรัน migration ซ้ำ, isolation ของผู้ติดตามสองบัญชี, รูปส่วนตัว และลำดับสถานะครบวงจร ยังไม่ทดสอบ LINE OAuth จริงหรือฐานข้อมูลปลายทาง


## ปรับปรุงแผนที่และระดับน้ำ

Migration `010_report_water_depth.sql` เพิ่มคอลัมน์ `water_depth` โดยรายงานเดิมเป็น unknown คำสั่ง `db:migrate:reports` รันทั้ง 009 และ 010 ขอบเขตนำมาจาก GISTDA รหัสจังหวัด 93 / อำเภอ 10 ชื่อภาษาอังกฤษ Pa Phayom (ต้นทางสะกดไทย “ป่าพยอม”) ดึงเมื่อ 8 ตุลาคม 2569 และเก็บ attribution ใน GeoJSON ใช้เพื่อแสดงบริบท ไม่บังคับปฏิเสธรายงานบริเวณใกล้เคียง เมื่อหมุดนอกขอบเขตจะแจ้งให้ตรวจสอบ ไม่ส่งพิกัดเริ่มต้นอัตโนมัติจนกว่าจะเลือกจุด GPS หรือลากหมุด

ตรวจปรับปรุงรอบนี้แล้ว: ปุ่มระดับน้ำทุกค่าและการปฏิเสธค่าที่ไม่รองรับ, การเก็บระดับน้ำ/พิกัดผ่าน API ใน PGlite, cookie กลับไป #report หลัง LINE และการป้องกัน URL redirect ภายนอก (mock LINE), หน้า guest ไม่แสดงฟอร์มก่อน login, เลือกจุดกลางแผนที่, ขยับและลากหมุดจริง, โหลดเส้นขอบเขต และ layout 320/390/1440 px ยังไม่ได้รัน migration 010 กับฐานข้อมูลปลายทาง


## รูปถ่ายหลายภาพ

Migration `011_multiple_report_photos.sql` เปลี่ยน primary key จาก report_id เป็น id ของรูป พร้อม filename และ sort_order โดยรักษารูปเดิมไว้ (ลำดับ 0) ดัชนี unique (report_id, sort_order) และ check 0–7 จำกัดสูงสุด 8 รูป หน้าแจ้งเหตุเลือกหลายรูป เพิ่มรูปได้หลายครั้ง แสดงตัวอย่างภาพพร้อมชื่อและลำดับ ลบภาพก่อนส่งได้ และคืน object URL เมื่อลบ/ออกจากฟอร์ม ขั้นตอนยืนยันแสดงจำนวนภาพที่เลือกไว้ API จำกัดขนาด body ขณะอ่าน stream และตรวจจำนวน/ขนาด/signature ของรูปทุกภาพก่อนเริ่ม transaction รูปทั้งหมดและรายงานบันทึกพร้อมกัน หากรูปใดบันทึกไม่ได้จะ rollback ทั้งรายงาน รายงานที่ส่งแล้วแสดงแกลเลอรีส่วนตัวในรายละเอียด

ตรวจรอบรูปหลายภาพแล้ว: migration 011 รักษารูปเดิมและรันซ้ำได้, API บันทึก/อ่านหลายรูปใน PGlite, จำกัดจำนวน/ขนาดและตรวจ signature, rollback เมื่อรูปถัดไปบันทึกไม่สำเร็จ, UI เลือกหลายรูป/เพิ่มทีหลัง/ลบ/แสดงตัวอย่างภาพที่ decode ได้/กลับขั้นตอน/เริ่มรายงานใหม่, multipart ส่งเฉพาะภาพที่คงไว้ และแกลเลอรีหลังส่งโหลดหลายภาพได้ (Playwright ใช้ข้อมูลและการส่งจำลอง) ยังไม่ได้รัน migration 011 กับฐานข้อมูลปลายทาง

## โซนแผนที่สถานการณ์

หน้า `#map` ใช้ `public/boundaries/pa-phayom-basin.geojson` ที่คัดลอกจาก https://pa-phayom-floodboard.dpakorn75.chatgpt.site/data/basin.geojson โดยตรง ไฮไลต์โซนลุ่มน้ำด้วยเส้นประสีเขียวอมฟ้าและลดสีพื้นที่ด้านนอก คงพิกัดและ properties ต้นฉบับ รวมขอบนอก 538 จุดและวงด้านใน 89 จุด แทนแนวประมาณที่แปลงจากภาพ/SVG ก่อนหน้า เป็นขอบเขตเดียวกับเว็บอ้างอิง ไม่ได้ยืนยันว่าเป็นขอบเขตที่หน่วยงานรับรอง และไม่ใช้จำกัดสิทธิ์หรือปฏิเสธรายงาน แผนที่เลือกหมุดแจ้งเหตุในหน้า `#report` ใช้ GeoJSON ชุดเดียวกัน พร้อมแจ้งเมื่อหมุดอยู่นอกโซน (ไม่ปิดกั้นการส่งรายงาน)
